# Guardrails checklist

A reference for designing guardrails and for answering "how do you make this LLM feature safe?" The build is in `modules/phase-4-ai/src/Phase4.ProductionAi/Guardrails/` (✅ = built there).

## What guardrails are
Guardrails are checks that code runs **before and after the LLM call**, and around every tool call. For each check the code decides one of four things:
- **Allow:** the text goes through unchanged.
- **Redact:** sensitive values are masked and the text continues.
- **Review:** a human decides.
- **Block:** the request stops and the user gets a safe reply.

The two kinds of check behave differently:
- **PII is sanitised:** it is masked and the text goes on.
- **Harmful content is judged:** it is allowed, sent for review or blocked, never "cleaned up".

```
user ─► INPUT GUARDS ─► LLM / agent (sees redacted text) ─► OUTPUT GUARDS ─► user
            │                    │ tool calls ─► ACTION GUARDS                 │
            └── block / review ──┴──────── every decision logged in the trace ─┘
```

**Two thresholds per score.** Below the review line the text is allowed. Between the review line and the block line, a human looks at it. At or above the block line it is blocked.
```
0 ──── review (0.5) ──── block (0.8) ──── 1
  allow     human review        block
```

## Input checks (before the model)
| Check | Catches | Usually done with |
|---|---|---|
| ✅ Length / size | Huge pastes that cost money or bury the instructions | Code |
| ✅ PII | Cards, emails, phone numbers, names, national IDs | Regex (Luhn for cards) and a PII service (Azure AI Language, Presidio) |
| ✅ Harmful content | Hate, violence, self-harm, sexual content, harassment | A moderation service (Azure AI Content Safety, OpenAI moderation) |
| Prompt injection / jailbreak | "Ignore your instructions…", role-play tricks, hidden text in files | Azure Prompt Shields or a classifier, **plus design defences** (sources treated as data, tool permissions) |
| Topic / scope | "Write my essay" sent to an order-support bot | A small classifier or a cheap LLM yes/no call |
| Secrets | API keys, passwords, connection strings pasted in | Regex for known formats (`sk-…`, `AKIA…`) and entropy checks |
| Encoding tricks | Base64, homoglyphs, invisible Unicode used to get past filters | Normalise the text first, then check it |
| Rate / abuse | One user flooding the endpoint, scripted attacks | Gateway rate limits (M8) and per-user token budgets |

## Output checks (before the user sees it)
| Check | Catches | Usually done with |
|---|---|---|
| ✅ PII leak | Another customer's data that came from a document or a tool result | The same PII redactor |
| ✅ Harmful content | Offensive text generated by the model | Moderation |
| Groundedness / hallucination | Claims that the retrieved sources don't support | A citation checker (Phase4.Rag), Azure groundedness detection, or an LLM judge given the sources |
| Policy / business rules | "Your refund is done" when no refund ran; promised discounts; legal or medical advice | Code rules plus checks against the real state (like the eval's state check) |
| System prompt leakage | The model revealing its instructions | Comparing the reply against the prompt text; canary tokens |
| Format | Broken JSON, missing fields, invalid enum values | Schema validation or structured output |
| Protected material | Copyrighted text or code reproduced word for word | Azure protected-material detection |
| Brand / tone | Rude or off-brand replies | An LLM judge or a classifier, usually run on a sample |

## Action checks (agents and tools)
| Check | Catches | Usually done with |
|---|---|---|
| Authorisation per tool call | The model acting on another user's data | Code inside the tool, with the identity taken from the token (`SupportTools` owner check) |
| Argument validation | Amounts over the limit, invalid ids, injected SQL | Typed parameters, enums and range checks |
| Human approval tiers | High-risk actions such as big refunds, deletes and external emails | An approval gate (Phase4.Agents) |
| Budgets and stop conditions | Runaway loops and cost blow-ups | Maximum steps, tokens and time (Phase4.Agents) |
| Data exfiltration | A tool sending private data outside (an email or a URL with data in it) | Allowlisted destinations; no "fetch any URL" tool |

## Around everything
- **Order:** run the cheapest checks first (code, then a classifier, then an LLM judge). Blocked or held input never reaches the model, so it costs nothing.
- **Decide fail-open or fail-closed for each check.** Built here:
  - If the PII service is down, **fail closed** (block), because sending unredacted data is the worse outcome.
  - If moderation is down, **fall back** to the in-code check instead of running no check at all.
- **Trace every decision:** which guard fired, its score and its action. You need this to tune thresholds and to find false positives.
- **Metrics:**
  - block rate;
  - size of the review queue;
  - false-positive rate, measured from the human reviews;
  - latency added by the guards.
- **Retention and access:** prompts and traces contain user data. Keep them for a limited time, restrict who can read them, and store the redacted text.
- **Guardrails are not the security boundary.** Classifiers miss things. What actually prevents leaks is code: authorisation in the tools and owner checks.

## In code vs. by calling an endpoint (built both)
| | In code (`RegexPiiRedactor`, `KeywordModerator`) | Endpoint (`AzurePiiRedactor`, `AzureContentSafetyModerator`) |
|---|---|---|
| Cost / speed | Free, microseconds | A network call (~100–300 ms) plus a price per call |
| Quality | Crude: an order number is masked as a phone number; "kill the process" vs. "kill you" depends on the word list | Understands meaning, context and many languages |
| Availability | Always up | Can fail, so it needs a timeout, retries and a fallback or fail-closed decision |
| Typical use | First cheap filter, and the fallback | The main check |

## Interview one-liner
"Guardrails run before and after the model and around every tool call. Input checks: length, PII redaction, moderation, injection and scope. Output checks: PII leaks, moderation, groundedness and business rules. Each check decides allow, redact, review or block, using two thresholds. They run cheapest first, each decision is traced, and each check has a deliberate fail-open or fail-closed choice. They're not the security boundary: authorisation in code is."
