### I1 answer (my words, 2026-11-24, saved as is)
> I use AI every day, at work and in my personal life: explaining unfamiliar codebases, debugging complex problems, doing deep research when working on something new and unfamiliar, troubleshooting production incidents, and writing up stories, documentation, ADRs and test plans.
>
> One recent piece of work was the SMTP migration: with the help of AI I was able to complete it following standards, with near-zero downtime.
>
> I still treat it as a tool. I never auto-allow; I always review everything, and I ask the AI to write code according to our standards.
- **Follow-up answers (my words, 2026-11-24, saved as is):**
  > AI performed research around which SMTP Linux processes are available. Then I described how the Windows one works and asked it to find the closest one. It laid out 2 options. I went through the official docs to verify them, then I made the final decision, picking the one closest to the Windows VM service that would serve our needs.
  >
  > I also asked AI to write up documentation and ADRs, based on the information I provided, for future reference and for any future migrations.
  >
  > As good as it is, it's also dumb in certain ways. When I ask it to write code following existing standards, it comes up with its own standards; and even when it does follow them, it creates the shells in the same standards but the insides don't follow them.
- **Grade after follow-ups:** 7/10. Now a real story: AI narrowed the options (research) → you verified against official docs → **you** made the call; AI wrote the ADRs so the next migration is faster. The "shell follows standards, insides don't" is a sharp, honest limitation (use it for I2).
- **Still missing:** the time saved (research ~days → ~hours?), the two options and why you picked one (one line), and how near-zero downtime was achieved.
- **Grade (I1, first answer):** 6/10. Good, realistic range of uses, and a clear review habit ("never auto-allow"). The example is there but not yet told.
- **To strengthen (❓):**
  - **Tell the SMTP migration as a mini-story (the gain is the point of the question):** what was migrated (from what to what), what AI did specifically (read the old code? generated the config / tests? wrote the cutover plan?), and the before/after: "would have taken ~X weeks, took ~Y days".
  - **"Near-zero downtime":** how (parallel run, DNS/config switch, rollback plan); that part was *your* engineering, so say it.
  - **"Following standards":** how: you gave it the team's conventions / ADRs / existing examples as context. That's a strong, specific technique.
  - **Name the tools** (e.g. Claude Code, Copilot, an internal assistant) and **the data rule** in a FedRAMP setting: what you never paste in (secrets, customer data, CUI).
  - **Add the builder angle in one line:** ST6 (Azure OpenAI vulnerability triage, weekly manual → daily automated). Most candidates only *use* AI; you've *built* with it.
  - Trim the list to 3 uses and go deep on one, rather than listing six.
- **Follow-ups to prep:** What did AI get wrong in the SMTP work and how did you catch it (→ I2)? How do you give it your standards? What would you never let it do (→ I3)?

I verify each file and identify whether there are any bugs; only then will I commit and create a PR. I follow the same with everything I use AI for. - **To strengthen (❓):**
  - **Add the specific miss** (you already have it from I1): "I asked it to follow our standards; the class shells matched, but inside it used its own [error handling / logging / data-access / validation] pattern. I caught it in my file-by-file review [or: a test failed / a reviewer flagged it]. Had it shipped, [inconsistent error handling / a missed retry / …]."

### I3 answer (my words, 2026-11-24, saved as is)
> I would never let it run any update statements on the DB. I would never let AI access any secrets or variables, never let it create or update any resources, never give it more than read-only access to any resources, never let it access sensitive data, and never let it auto-approve its own output.
- **Grade (I3):** 6/10. A solid, correct list centred on read-only access, secrets, data and self-approval.
- **To strengthen (❓):**
  - **Open with the principle** that ties the list together: "AI can propose anything; a human approves anything irreversible, security-sensitive or customer-facing." Then the list reads as judgment, not a memorised set of rules.
  - **A reason per item** (one clause each): updates are hard to reverse; secrets in a prompt can leak into logs/providers; resource changes have a blast radius; sensitive data must stay in approved systems.
  - **Enforcement, not intention:** least-privilege / read-only tokens for agents, no prod credentials in dev tools, branch protection + required reviews, pipeline approval gates, audit logs.
  - **Missing items worth one line:** merging/deploying to prod without review; changing security controls (authz checks, policies, the FedRAMP boundary).
  - **Over-reliance:** "if I can't explain the code, it doesn't ship."
  - **Proof you've built this:** the Phase 4 agent (reads + small refunds automatic, above a limit needs human approval, identity checked in code) and policy-as-code through a reviewed pipeline (ST5).
- **Follow-ups to prep:** Isn't read-only too restrictive for an agent to be useful? How would you let an agent fix a bug end to end safely? What's your view on agents opening PRs?

### ST6 · Azure OpenAI vulnerability-triage tool (weekly manual → daily automated) (Citrix)
- **Answers:** I7, I1, I2, I6, B6
- **Known (resume / notes):** C# tool on Azure OpenAI that triages security vulnerabilities end to end: classifies issues, finds the owning team, auto-creates Jira tickets; replaced a manual weekly review with an automated daily run.
- **Situation:** ❓ How many vulnerabilities a week, who did the manual review, how long it took
- **Task (my job in it):** ❓ Your idea? Built solo?
- **Action (what I did: "I", not "we"):** ❓ How you checked the classifications before trusting them (a labelled sample? side-by-side with humans?); what happens when it's wrong; how teams came to trust auto-created tickets
- **Result (numbers):** Weekly → daily; ❓ hours saved; ❓ accuracy you measured
- **What I'd do differently:** ❓
- **Follow-ups to prep:** How did you validate it? A time it was wrong? Did teams trust the tickets? What would you never let it do on its own?
- **My answer for I7 (my words, 2026-11-24, saved as is):**
  > There was a problem: the gov compliance data sits in a DB within the boundary, and someone had to check the data and then create tickets manually for all the teams.
  >
  > I proposed creating an AI agent, as this was a good candidate because the data classification can be probabilistic. I created a C# tool that reads the data from the DB. The data already has tags that identify which team a resource belongs to; if the tags exist, there's no AI agent involvement, and the tool creates tickets for the resources whose vulnerability is past due.
  >
  > A few resources don't have tags. It's the teams' responsibility to tag them, but some aren't tagged. This is where the AI agent shines. I created mappings to identify which resources belong to which team, using the subscription and the resource naming convention. But sometimes the naming convention doesn't match, and in that case the agent's probabilistic approach can analyse and create tickets, with human approval if the confidence is low.
  >
  > Every day the agent runs on a schedule, with a system prompt saying it's an agent that classifies vulnerability data across teams and creates tickets. The tool passes in the mappings I created so it can identify which team each resource belongs to, then it creates tickets accordingly. There's a human-in-the-loop case: if it doesn't have enough confidence, the tickets are routed to people, who review them and assign them to the right teams.
  >
  > Initially teams were a little sceptical about this process, so I brought in one team at a time. Once everyone saw how accurate it was, slowly all the teams were onboarded.
- **Grade (I7):** 7.5/10. Strong design judgment: **deterministic first** (tags → no AI), AI only for the untagged remainder, mappings (subscription + naming) as context, low confidence → human review queue, and adoption **one team at a time**. That's "the model classifies, code acts" exactly.
- **To strengthen (❓):**
  - **How you knew it was accurate (the core of the question):** e.g. ran it side by side with the manual process for N weeks, or checked a labelled sample; the agreement rate; how often humans reassigned its tickets. "Everyone saw how accurate it was" needs a number.
  - **Where "confidence" comes from:** an LLM's self-reported confidence is unreliable on its own. Say what it was (score in structured output + rules such as "no mapping match → review"?) and how you tuned the threshold.
  - **A time it was wrong:** one example, how it was caught (a team bounced the ticket?), and what you changed (a mapping, the prompt, a new rule).
  - **Feedback loop:** reassignments from the review queue fed back into the mappings / test cases.
  - **Fixing the root cause:** did untagged resources go down (e.g. a policy requiring tags, or reports to teams)?
  - **Numbers:** resources per day, % untagged, % sent to review, hours saved vs. the manual weekly review, weekly → daily.
  - **One line on data:** the model endpoint was inside the boundary / approved for that data (Azure Government OpenAI?).
- **Follow-up answers (2026-11-24):**
  - **Why an LLM, not fuzzy matching:** names didn't always follow the convention, so the model reasoned over the name together with the subscription, resource type and my mappings.
  - **Where the model ran:** Azure OpenAI in Azure Government (FedRAMP High), inside the boundary, called with managed identity (no API keys). Prompts aren't used for training; in Azure Government, abuse-monitoring storage/human review is off (verify against current docs before stating it).
- **Follow-ups to prep:** How did you measure accuracy? How was confidence computed? What happens to a ticket created for the wrong team? Why use an LLM rather than fuzzy matching on names?
