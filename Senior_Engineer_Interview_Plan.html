1. Program overview

This program covers Low-Level Design (LLD), .NET platform internals, distributed systems implementation, High-Level Design (HLD) and architecture, AI engineering (LLM applications, RAG, inference, agents and evals), AI-assisted coding and the newer round types, behavioral and leadership preparation, resume positioning, and mock interviews. It assumes professional experience with C#, .NET, APIs, cloud services and microservices, and it puts engineering decisions and failure handling ahead of beginner CRUD material. DSA is out of scope.

There is no calendar. Finish each module when its exit deliverable is met, then move on. A short checkpoint mock closes each phase so weak areas show up early, not in the last module.

2. How to work through a module

  1. Review your notes first. The 🟧 box lists the matching Apple Notes. Read them, then read section 10 for any corrections that apply.
  2. New Concept first, for every topic (each principle, pattern, LLD problem, distributed-systems concept, HLD pattern or case, AI topic), before any code:
    1. In plain words: what it is, in one or two sentences.
    2. The problem it solves: what goes wrong without it, as a concrete scenario.
    3. An analogy that makes it stick.
    4. A small diagram: the happy path, then the failure path.
    5. Variations and alternatives (e.g., orchestration vs. choreography; Saga vs. 2PC).
    6. When not to use it.
    7. Quick check: answer 2–3 questions in your own words, then write the topic's entry in the module README's Concepts section.
    For an LLD problem, steps 1–2 are the requirements and the hard part, and step 4 is the class diagram. For an HLD case, steps 1–2 are the product and its core scaling problem, and step 4 is the architecture.
  3. Understand the internals: study how it works, its guarantees and trade-offs in depth.
  4. Implement: write C#, configure infrastructure, build data access, add tests.
  5. Experiment: inject failures, concurrency, delays, restarts, duplicates and load. Tick the matching items in section 4.
  6. Interview practice: draw the design, explain decisions, answer follow-ups out loud.
  7. Journal it using section 9, then tick the module's Done box. The box is only for when the exit deliverable is met.
Checkpoint mocks

At the end of each phase, do one short (30–45 min) mock covering that phase. Use a peer, a platform, or record yourself. Score it against the rubric in M32. If a checkpoint shows a gap, go back to that module before starting the next phase.

New Worked example 1: one change applied to 100k users (Azure)

  • First, avoid the fan-out if you can (interviewers listen for this): apply the change at a higher level, such as Entra group-based assignment, dynamic groups, Conditional Access, or role assignments at a broader scope.   • API: submit a job, return 202 Accepted with a job ID, then poll a progress endpoint or push status (SignalR/SSE/webhook). Support dry run and cancel.
  • Orchestration: Durable Functions fan-out/fan-in, or a Service Bus queue with a worker pool. Chunk users (e.g., 500 per chunk) and checkpoint every chunk.
  • Graph limits: use JSON $batch (up to 20 requests per call). Graph throttles per app and per tenant, so honor Retry-After, add jitter, and use adaptive concurrency. Throttling, not compute, is the real bottleneck.
  • Idempotency: each item must be safe to apply twice (“set to X”, never “toggle”). Store status per user so a rerun only touches failures.
  • Rollout and verification: dry run → canary 1% → waves. Verify with a delta query. Keep an audit log, a per-user error report, and a kill switch. Rollback is the same job run in reverse.

New Worked example 2: one schema change across 10k tenant databases

  • Tenant catalog: a central list of every tenant DB, each with a schema_version and wave/region/size tags.
  • Expand/contract: the app must work with schema N and N+1 while the rollout is in flight. Only expand (add columns or tables) during the rollout; contract (drop the old shape) in a later release once every DB is migrated.
  • Execution: Azure SQL Elastic Jobs or your own orchestrator, running idempotent migration scripts (DbUp, EF migration bundles, or DACPAC) recorded in a per-DB version table.
  • Concurrency limits: cap how many DBs migrate at once per elastic pool/server so tenants on the same pool don't starve. Use ONLINE=ON and resumable index operations, and schedule in each region's off-hours.
  • Waves: internal tenants → 1% → 10% → all, with an automatic halt on error-rate or latency thresholds. Migrate the largest tenants separately.
  • Failures: retry transient errors; quarantine persistent ones in a “failed DBs” list. Prefer rolling forward; keep rollback scripts only for the expand step.
  • Observability: a dashboard of DB count per version, stragglers, and per-migration duration.

5. Deep-dive implementation requirements

5.1 Queue delivery guarantees

  • Distinguish publisher confirms from consumer acknowledgements; they protect different stages.
  • Understand at-most-once, at-least-once, and effectively-once business processing.
  • Treat duplicate delivery as normal; use durable idempotency at the business boundary.
  • Understand routing failures, durability, prefetch, redelivery, ordering, competing consumers, and backpressure.
  • Compare RabbitMQ acknowledgement/queue behavior, Kafka partition/offset behavior, and Azure Service Bus locks/settlement.

5.2 Retry architecture

  • Classify transient and permanent failures before retrying.
  • Use exponential backoff with jitter, maximum attempts, retry budgets, and an overall deadline.
  • Avoid nested retry amplification across HTTP, database, and consumer layers.
  • Recognize uncertain outcomes: timeout does not prove an operation failed.
  • Use delayed retries and DLQ for exhausted/poison messages; design replay as a controlled operational workflow.

5.3 Transactional outbox and inbox

  • Commit business state and outbox record in the same local database transaction.
  • Assume relay publication can be duplicated if it crashes after publish but before recording success.
  • Use safe concurrent claiming/leases; recover abandoned claims and preserve per-aggregate ordering where required.
  • Commit inbox deduplication record and consumer business changes in the same local transaction.
  • Plan schema evolution, retention, cleanup, CDC versus polling, backlog monitoring, and replay.

5.4 Multiple databases and distributed transactions

  • Understand that two independent local commits do not automatically form one atomic transaction.
  • Reproduce partial commit and uncertain commit outcomes.
  • Study 2PC and its coordinator, prepare/commit, blocking, timeout, and operational constraints.
  • Use Saga for long-running business workflows where local transactions and compensation are appropriate.
  • Persist Saga state; make steps and compensations idempotent; recover after process restart.
  • Treat compensation as a new business operation that can fail, not as a magical rollback.

5.5 SQL concurrency and locking

  • Reproduce dirty reads, non-repeatable reads, phantom reads, lost updates, write skew, and deadlocks.
  • Use rowversion/optimistic concurrency and understand when pessimistic locks are justified.
  • Handle SQL Server deadlock error 1205 by retrying the correct transaction boundary with bounded randomized delay.
  • Understand lock escalation, long transactions, blocking, snapshot isolation, and connection-pool pressure.
  • Measure throughput and tail latency under concurrent load.

5.6 Distributed locks

  • Understand lock acquisition, lease expiry, renewal, ownership, and safe release.
  • Simulate pauses that outlive the lease and demonstrate stale lock holders.
  • Use fencing tokens when stale owners must be prevented from writing.
  • Compare database coordination with Redis-based coordination and identify when a distributed lock is unnecessary.

5.7 .NET async and runtime

  • Understand how async/await compiles to a state machine and resumes on the ThreadPool or a captured context.
  • Avoid sync-over-async; diagnose ThreadPool starvation with dotnet-counters and dotnet-trace.
  • Propagate CancellationToken through HTTP, database, and messaging calls; honor overall deadlines.
  • Use Channels for bounded producer/consumer pipelines with backpressure.
  • Understand GC generations, the LOH, and allocation pressure; use Span<T>, Memory<T>, and ArrayPool where they matter.

5.8 New ASP.NET Core and EF Core

  • Know the DI lifetime rules and how a captive dependency happens; create scopes explicitly in background work.
  • Use IHttpClientFactory or typed clients with resilience handlers; never create HttpClient per call.
  • Read-only queries use AsNoTracking and projections; never rely on lazy loading for performance.
  • DbContext is not thread-safe: scoped per request, IDbContextFactory elsewhere, never singleton.
  • Migrations ship as reviewed, idempotent scripts using expand/contract for zero-downtime deploys.

5.9 New Messaging frameworks (NServiceBus / MassTransit)

  • Know exactly what the framework's outbox guarantees and where its deduplication state lives.
  • Configure immediate and delayed retries deliberately; know where exhausted messages go and how they are replayed.
  • Sagas: correlation properties, persistence, concurrency control, timeouts, and completion.
  • Version message contracts additively; run old and new contracts side by side during migrations.

5.10 Streaming and event sourcing

  • Choose partition keys for ordering and even distribution; understand the impact of rebalancing.
  • Commit offsets only after durable processing, and combine this with idempotent consumers.
  • Know what Kafka exactly-once covers (read-process-write within Kafka) and what it does not (external side effects).
  • Evolve event schemas compatibly; plan projection rebuilds and snapshotting.

5.11 API design and security

  • Make unsafe operations idempotent with client-supplied keys and stored responses.
  • Use cursor pagination for large or changing datasets; version APIs without breaking clients.
  • Validate tokens fully (issuer, audience, signature, expiry); enforce object-level and tenant-level authorization on every request.
  • Use authorization code + PKCE for user sign-in; keep tokens out of JavaScript-readable storage where possible (BFF).
  • Sign webhooks, include timestamps to prevent replay, and make receivers idempotent.

5.12 New Real-time delivery

  • Pick polling, SSE, or WebSockets based on direction, frequency, and infrastructure constraints.
  • Scale out with a backplane or managed service; know what happens to in-flight messages when a node dies.
  • Design reconnect with jittered backoff and a resync step (last-seen sequence number) so clients never silently miss state.
  • Treat push notifications as best-effort; the source of truth is always fetchable.

5.13 New Architecture and migrations

  • Draw service boundaries around bounded contexts and data ownership, not around tables or teams' convenience.
  • Prefer a modular monolith until independent scaling, deployment, or ownership demands a split.
  • Migrate incrementally (strangler fig, parallel run, CDC sync) with a rollback path at every step.
  • Record significant decisions as ADRs with the alternatives you rejected.

5.13a New Long-running bulk operations

  • First ask whether the change can live at a higher level (group, policy, tenant default) or be applied lazily, so no fan-out is needed.
  • When fan-out is needed: job ID + progress, chunking with checkpoints, idempotent per-item operations, per-item status, throttling that respects downstream limits, waves with automatic halt, and verification after completion.
  • For fleets of databases: expand/contract so the app tolerates mixed versions, a catalog tracking each DB's version, bounded concurrency per pool, and quarantine for failures.

5.13b New Payment exactly-once

  • One idempotency key per checkout attempt, created before the first try and reused on retries; enforced by a unique constraint server-side and passed through to the payment provider.
  • Only one successful payment per order, enforced by the database, not by the UI.
  • A timeout is an unknown outcome: query or retry with the same key, never a new one; reconcile against provider reports.

5.14 RAG and retrieval

  • Treat retrieval quality as measurable: recall@k, precision, and answer faithfulness.
  • Combine lexical and vector retrieval (e.g., RRF); rerank before context assembly.
  • Apply tenant and permission filters inside the retrieval query, never only in the prompt, and never trust LLM-generated filters for authorization.
  • Plan re-indexing for content changes, deletions, and embedding-model upgrades.

5.15 New LLM inference and adaptation

  • Estimate GPU memory as weights + KV cache, and know which knob (quantization, batching, context limit) moves which number.
  • Track TTFT, TPOT, throughput, and cost per request; know why prefill and decode scale differently.
  • Exhaust prompting and retrieval before fine-tuning; fine-tune only with an eval set that proves the gain.

5.16 Agents, evals, and LLM security

  • Give agents the minimum tools and permissions needed; require approval for irreversible actions.
  • Bound every agent run with step, time, and cost budgets and explicit stop conditions.
  • Treat all retrieved and tool-returned content as untrusted input.
  • Gate releases on eval results; never ship a prompt or model change without a regression run.
